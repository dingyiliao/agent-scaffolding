# Project Comparator

Produces a comparison report across multiple project analyses.

## Inputs

The user provides **2 or more** project analysis reports (markdown files). These can be:
- Reports previously generated by the `project-analyzer` skill (preferred — structure is predictable)
- Any structured markdown analysis of a project

If the user mentions project names but provides no reports:
- Ask whether reports already exist at known paths
- If not, suggest running `project-analyzer` first on each project, then come back

If the reports are at mixed analysis depths (one `quick`, one `deep`), proceed but **call this out at the top of the comparison** — the comparison will have asymmetric detail.

## Workflow

### Step 1 — Read all reports

Read each report fully. For each, extract:
- Project name
- Analysis depth (from filename suffix or report header, if present)
- Generation date (from header `**生成日期**:` line if present — used for staleness checks in pitfalls)
- Core sections present
- **modules section + TOP-N score table if present** — analyzer-generated reports include a structured module list (with LoC, key entries) and a normalized score table; these are the highest-quality cross-comparison signal and must not be skipped

If a report lacks an explicit modules section (hand-written analyses, older reports), record this and fall back to the "实现 / 架构" / "代码组织" prose for the same information.

### Step 2 — Build comparison content

**Always cover these four core dimensions** in priority order:

#### 1. 模块对齐 (Module cross-mapping)

This dimension comes first because it grounds every later claim in structured data from the source reports. **Only applicable when at least one source report has a modules section** (analyzer-generated). Skip with a one-line note if all reports are hand-written prose without module decomposition.

Steps:
1. Build a **module overlap matrix**: union of all module names across projects on rows, projects on columns. Cell values:
   - ✅ present (with LoC if available)
   - ⚠️ partial / different scope (use when a module exists but covers materially different concerns — e.g., A's `auth` does OAuth + RBAC, B's `auth` is just session tokens)
   - ❌ absent
   - ❓ source report lacks modules section
2. **Name normalization**: don't require exact name match. `routing` / `router` / `routes` / `dispatch` are usually the same concern. List the normalization decisions explicitly so readers can disagree.
3. **TOP-N ranking comparison**: if reports have TOP-N score tables, show *"在 A 眼里这是核心模块，但在 B 那里是边缘"* by ranking the same module across projects.
4. **Independent modules**: list modules unique to each project below the matrix. These often reveal differentiating bets.

This section is **factual**, not evaluative — it should not contain "选择 A 因为…" style language. Save judgment for "适用场景建议".

#### 2. 特性覆盖对比 (Feature coverage)
- Build a feature matrix: rows = features, columns = projects
- Cell values: ✅ native / 🔌 via plugin / ⚠️ partial / ❌ none / ❓ unknown (not in report)
- Highlight features unique to each project below the matrix
- **Feature matrix vs module matrix**: features are user-facing capabilities ("支持 OAuth"、"提供 SDK"), modules are code-organization units. The two often overlap but are not the same — keep both when both yield distinct insight; drop the feature matrix if it would just repeat the module matrix.

#### 3. 解决问题的思路差异 (Design philosophy differences)
- Side-by-side description of each project's core abstractions
- Identify the underlying mental model — what does each project assume about the world?
- Note where the projects diverge in fundamental approach (e.g., synchronous vs event-driven, declarative vs imperative)

#### 4. 性能 / 资源取向 (Performance / resource orientation)
- Memory model, concurrency model, IO model
- Throughput-oriented vs latency-oriented
- Assumed deployment scale (cloud-scale / single-machine / embedded / browser)
- Where the cost goes (memory / CPU / network / storage)

**Optional dimensions** — include only if the source reports cover them:
- Maturity / production-readiness
- Ecosystem / community
- License / governance
- Learning curve / DX

### Step 3 — Generate the comparison report

**Output path:** under the current working directory's `./reports/`. Create the directory if missing.

- 2 projects: `./reports/<A>_vs_<B>_comparison.md`
- 3+ projects: `./reports/<A>_and_<B>_and_<C>_comparison.md`

**Filename rules (ASCII only):**
- Use ASCII characters only — no CJK / accented / emoji. The report **content** stays in 简体中文 per the style guide; only the filename is ASCII.
- Sanitize each project name: strip `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, and whitespace (replace with `-`).
- If a name conflict would occur (`A_vs_B_comparison.md` already exists), append a short discriminator (e.g., the source-report depth: `A_vs_B_comparison_medium.md`).

**Report skeleton:**


### Step 4 — Present the report

After writing the file:

1. Print the **absolute path** to the report. Resolve with whatever the environment provides — `realpath ./reports/<file>` on bash, `Resolve-Path ./reports/<file>` on PowerShell.
2. In chat, give a 2–3 sentence summary of the headline finding — don't restate the report.
3. Tell the user: *"已写入 `<absolute path>`，可在编辑器中打开。"*

Do not assume any sandbox-only presentation helper exists.

## Comparison pitfalls

Before finalizing the comparison, audit it against the following signals. Each is a known way comparisons go wrong; surface the relevant ones at the top of the report (alongside the asymmetric-depth warning) so readers can calibrate trust.

| Pitfall | What to look for | How to handle |
|---|---|---|
| **Stale report mix** | Source reports generated > 6 months apart, or one report dated > 12 months ago | Add a header warning. Flag any feature claim that may have been added/removed since the older report. Suggest re-running analyzer on the older project if a decision is at stake. |
| **Quality asymmetry** | One report is analyzer-generated with all required dimensions, the other is short prose / marketing-flavored / missing the "客观事实 vs 主观评价" split | Prefix TL;DR with a quality-asymmetry warning. Avoid drawing conclusions from dimensions where only one side has rigorous data. |
| **Depth asymmetry** | Reports at different analyzer depths (`quick` vs `deep`) | Existing pattern: warn at top of TL;DR. Avoid claiming "B doesn't have X" when B was only `quick`-analyzed — say "未在 B 的 quick 报告中体现". |
| **Cross-ecosystem comparison** | Comparing across language ecosystems (e.g., Go vs Node vs Rust) | Performance/resource dimensions need extra care — idiomatic numbers differ by ecosystem. Avoid raw number comparison; prefer ratios or qualitative tiers. License/dependency conventions also differ. |
| **Unsupported numerical claims** | A source report contains numbers like "3x faster than X" without benchmark methodology | Do **not** propagate these into the comparison. Either find the methodology in the source repo or treat the claim as marketing. |
| **Same-author / fork relationship** | Projects from the same author/org, or one is a fork/rewrite of the other | Focus comparison on **what changed and why** (the deltas). For forks, comparing every shared dimension wastes space — start from the divergence point. |
| **Marketing-language contamination** | One source report quotes README hyperbole as fact (e.g., "8-stage pipeline" when analyzer flagged it as 7) | Re-anchor on the analyzer's "README hyperbole vs code reality" notes from the source report; don't carry the README claim into the comparison. |
| **Module name collision without overlap** | Two projects both have a module called `core` / `service` / `manager` — generic names, very different scope | In 模块对齐 normalization, treat as ❌ rather than ✅ unless responsibilities actually overlap. Note the collision explicitly. |

## Notes and edge cases

- **Don't fabricate.** If a dimension can't be compared because it's not in the source reports, say "未在源报告中体现" rather than guessing. This is especially important for performance claims.
- **Asymmetric depth warning:** if depths differ, prefix the TL;DR with a note like *"⚠️ A 是 deep 分析、B 是 quick 分析，对比可能在某些维度上偏向 A 更详细。"*
- **4+ projects strategy:** the matrix format scales, but narrative sections collapse. Choose one based on the project set:
  - **Cluster-first**: if projects naturally group (e.g., "三个 Go 后端框架 + 一个 Rust 框架"), present groups first, then within-group comparison, then cross-group differences. Cuts page count significantly.
  - **Transpose**: if comparing many projects across few dimensions, put projects on rows and dimensions on columns. Reads better than 8-column tables.
  - **Eliminate-first**: open with a "为什么排除了 X、Y" 段落 if some candidates are obviously unsuitable (license / scale / maturity). Then deep-compare the remaining 2–3.
  - **Avoid**: trying to give every project a full "核心思路" paragraph — at 5+ projects this becomes unreadable.
