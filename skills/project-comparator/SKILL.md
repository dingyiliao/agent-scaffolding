# Project Comparator

Produces a comparison report across multiple project analyses.

## Inputs

The user provides **2 or more** project analysis reports (markdown files). These can be:
- Reports previously generated by the `project-analyzer` skill (preferred — structure is predictable)
- Any structured markdown analysis of a project

If the user mentions project names but provides no reports:
- Ask whether reports already exist at known paths
- If not, suggest running `project-analyzer` first on each project, then come back

If the reports are at mixed analysis depths (one `quick`, one `deep`), proceed but **call this out at the top of the comparison** — the comparison will have asymmetric detail.

## Workflow

### Step 1 — Read all reports

Read each report fully. For each, extract:
- Project name
- Analysis depth (from filename suffix or report header, if present)
- Core sections present

### Step 2 — Build comparison content

**Always cover these three core dimensions** in priority order:

#### 1. 特性覆盖对比 (Feature coverage)
- Build a feature matrix: rows = features, columns = projects
- Cell values: ✅ native / 🔌 via plugin / ⚠️ partial / ❌ none / ❓ unknown (not in report)
- Highlight features unique to each project below the matrix

#### 2. 解决问题的思路差异 (Design philosophy differences)
- Side-by-side description of each project's core abstractions
- Identify the underlying mental model — what does each project assume about the world?
- Note where the projects diverge in fundamental approach (e.g., synchronous vs event-driven, declarative vs imperative)

#### 3. 性能 / 资源取向 (Performance / resource orientation)
- Memory model, concurrency model, IO model
- Throughput-oriented vs latency-oriented
- Assumed deployment scale (cloud-scale / single-machine / embedded / browser)
- Where the cost goes (memory / CPU / network / storage)

**Optional dimensions** — include only if the source reports cover them:
- Maturity / production-readiness
- Ecosystem / community
- License / governance
- Learning curve / DX

### Step 3 — Generate the comparison report

**Output path:**
- 2 projects: `/mnt/user-data/outputs/对比_<A>_vs_<B>.md`
- 3+ projects: `/mnt/user-data/outputs/对比_<A>_and_<B>_and_<C>.md`

Sanitize project names for filenames (drop `/` and other path-unsafe chars).

**Report skeleton:**

```markdown
# 项目对比：<A> vs <B> [vs <C> ...]

- **对比项目**: <list with source report paths>
- **生成日期**: YYYY-MM-DD
- **来源报告深度**: <list per project, flag if asymmetric>

## TL;DR

3–5 lines: who wins on what dimension, the key trade-offs, and a one-sentence recommendation for the most common use case.

## 特性覆盖

| 特性 | <A> | <B> | <C> |
|---|---|---|---|
| ... | ... | ... | ... |

**各项目独有特性**:
- **<A>**: ...
- **<B>**: ...

## 解决思路差异

### <A> 的核心思路
...

### <B> 的核心思路
...

### 关键分歧点
...

## 性能 / 资源取向

| 维度 | <A> | <B> | <C> |
|---|---|---|---|
| 并发模型 | ... | ... | ... |
| 内存特征 | ... | ... | ... |
| 适用规模 | ... | ... | ... |

## 适用场景建议

- **选 <A> 如果**: ...
- **选 <B> 如果**: ...
- **都不太合适如果**: ...

## [可选灵活章节，根据源报告内容]
```

**Style:** Inherit from the source reports.
- All sources `standard` → output `standard`
- All sources `concise` → output `concise`
- Mixed → default to `standard` (lower bar for accessibility)

### Step 4 — Present the report

Call `present_files` with the comparison report path. In chat, give a 2–3 sentence summary of the headline finding — don't restate the report.

## Notes and edge cases

- **Don't fabricate.** If a dimension can't be compared because it's not in the source reports, say "未在源报告中体现" rather than guessing. This is especially important for performance claims.
- **Asymmetric depth warning:** if depths differ, prefix the TL;DR with a note like *"⚠️ A 是 deep 分析、B 是 quick 分析，对比可能在某些维度上偏向 A 更详细。"*
- **More than 4 projects:** the matrix format starts to dominate. That's fine. Consider splitting "解决思路差异" into a per-project list rather than narrative paragraphs.
- **Same-author comparisons:** if comparing different versions or related projects from the same author/org, focus extra attention on what changed and why — those decisions are more informative than for unrelated projects.
